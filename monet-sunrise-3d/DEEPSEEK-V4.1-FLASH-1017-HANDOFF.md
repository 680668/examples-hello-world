## 2. 总体目标：绘画本身成为三维空间

当前项目技术栈为 TypeScript、Three.js、GLSL 和 Vite。目标是将它演进为可进入、可穿越、能够近距离观察笔触的实时绘画场景。

### 2.1 核心原则

- 主要笔触必须拥有空间坐标、长度、宽度、曲率、颜色、深度和可控的厚度/隆起。
- 通过自定义 \`BufferGeometry\` 生成弯曲、渐细的 Ribbon（带状笔触）。
- GPU 顶点 Shader 负责局部、连续、低幅度的动态位移。
- Fragment Shader 负责克制的颜料沟槽、中心隆起高光和局部色彩变化。
- 使用合并几何体、共享材质或合适的实例化方案降低 Draw Calls。
- 远距离保留整体绘画构图；靠近时能发现独立笔触与真实空间层次。
- 动画服务于绘画的构图与节奏，不要把画面做成无主题的粒子屏保。

### 2.2 不要采用的捷径

- 不要把整幅原画当作主要纹理贴到一张平面上。
- 不要只对全屏画面运行旋涡 Shader 就称作三维绘画。
- 不要用普通 Points 粒子代替具有宽度、方向和形态的笔触。
- 不要仅增加粒子数、Bloom 强度或后处理来掩盖构图与几何体问题。
- 不要把莫奈的画面改造成高对比、密集、强旋涡的梵高式效果。
- 不要在未测试移动设备性能的情况下宣称移动端帧率达标。
- 不要引入没有来源记录或许可证核查的外部模型、图片或代码。

## 4. 三维笔触几何体

### 4.1 数据与几何

每条笔触至少有：

- 中心路径或可采样曲线；
- 长度、宽度和渐细轮廓；
- 颜料颜色；
- 深度或局部高度；
- 横截面/中心隆起参数；
- 运动相位；
- 流场影响强度；
- 所属区域（天空、普通海面、太阳倒影）；
- 适当的方向/切线信息。

使用采样点创建带状几何体。笔触边缘应当自然渐细，避免大量笔触都像截断的矩形条。部分关键近景笔触可以使用有更多横截面顶点的结构或封闭的浅体积；远景则采用低开销 Ribbon。

应检查顶点绕序、法线方向、双面材质的实际必要性、深度测试、包围球和相机近距离效果。几何体至少要在接近水面的视角下仍有明确轮廓。

### 4.2 颜色与构图

根据画面位置和艺术角色决定颜色，而非完全随机选色。随机仅用于小幅变化，不能破坏整体配色。

- 天空使用蓝灰、青绿、灰黄、暖橙等协调的晨光色。
- 太阳倒影应当具有明显的暖色带，但不是一条均匀的橙色矩形。
- 普通水面以蓝绿、青灰、低饱和暖色为主，保留不规则明暗节奏。
- 远处笔触更细，近处笔触更宽、更明显；不要形成规则网格。
- 控制色彩、宽度和间距的重复感，避免程序化的机械平铺。

### 4.3 确定性

使用固定种子生成主要笔触布局，确保每次启动时构图基本一致。这样才方便进行前后截图对比。随机动画相位可以存在，但不应每次重载都把核心画面完全打乱。

### 4.4 合并渲染

不要为每条笔触创建独立 Mesh。按区域、材质和必要的深度/裁剪策略合并为少量 BufferGeometry 或合适的实例批次。记录大致笔触数、顶点数和 draw call 数；如有瓶颈，根据数据调整，而非无限提高数量。

## 5. GPU 流场：天空和海面应当不同

### 5.1 天空流场

目标是表现清晨空气、云层和画面色彩的缓慢变化，而不是复制梵高《星月夜》的强旋涡。

可考虑：

- 低频平滑矢量场；
- Curl Noise 或其轻量近似；
- 与太阳位置/地平线有关的弱切向分量；
- 依空间距离和高度衰减的局部扰动；
- 每条笔触独立的相位和微弱形变。

天空的主形态首先来自初始几何布局；流场只做克制的动态扰动，不应让每帧图像的构图不断崩坏。

### 5.2 海面流场

以水平方向移动为主，并添加较小、连续的垂直变化：

- 低频水波；
- 笔触沿水平方向的轻微漂移；
- 局部高度变化；
- 不同笔触相位导致的错动；
- 太阳反光处轻微更活跃的高亮变化。

海面应当像由颜料短笔触描绘的水面，而非塑料、金属或发光网格。

### 5.3 倒影路径

倒影是场景的重要视觉锚点。建议独立生成暖色笔触集合：

- 空间上大致关联远处太阳与前景水面；
- 越接近太阳，反光的整体宽度和亮度可不同于近景；
- 近景可以有较宽、较断续的高亮笔触；
- 用不规则间距、宽度和方向变化表现水面破碎反光；
- 使基础水面颜色连续，真正的高亮细节由笔触几何体提供。

禁止用离散的方块 Hash、棋盘式阈值或不恰当低分辨率采样做主要反光结构。

### 5.4 Shader 质量门槛

检查并实际运行：

- Shader 编译；
- attribute / varying 类型是否匹配；
- uniform 是否正确更新；
- 坐标系和空间变换；
- 深度测试和透明度；
- Tone Mapping 与颜色空间；
- GPU 动态位移后几何体的裁剪边界；
- 浏览器窗口改变尺寸后的效果。

TypeScript 编译成功并不等于 GLSL 已正确运行。必须以浏览器与控制台证据验证。

## 6. 太阳、港口、船只与空气

保留这些元素并改进它们与笔触世界的关系。

### 太阳

- 作为初始构图和镜头探索的主要视觉中心。
- 核心色彩清晰，光晕层次丰富但不过曝。
- 减少无必要的高密度随机光线；避免让太阳变成尖刺球或科幻爆炸。
- 让海面倒影与太阳位置关联。

### 港口和水平线

- 保持远处港口剪影的可读性。
- 港口、桅杆、船只与水平线要提供稳定的空间参照。
- 不应被雾、太阳光晕或文字 UI 全部淹没。

### 船只

- 形体应当清楚，不要只像不规则的三角锥。
- 靠近镜头时避免明显穿模；远近船只要体现空间尺度。
- 保留克制的、与水面波动相符的轻微动态。

### 大气

- 少量颗粒可以补充空气质感，但不能代替绘画笔触。
- 使用薄雾增加深度时应谨慎控制强度。
- 避免大范围泛白导致原画的港口和海水层次消失。

## 7. 电影化运镜与交互

保留项目当前有效交互，并把镜头体验组织成完整旅程：

1. 开场：完整呈现画面，先保证原画构图的辨识度。
2. 接近：缓慢向太阳、远景水面移动，让画面逐步产生空间深度。
3. 下降：靠近海面，看到前后笔触的视差、宽度和高度差。
4. 倒影：沿太阳倒影移动，近距离观察暖色颜料笔触。
5. 回望：逐渐抬升，重新呈现太阳、船只、港口和水平线。
6. 返回：可以平滑回到开场状态。

实现建议：

- 用连续插值或 Catmull-Rom / 三次样条规划位置和 LookAt 目标。
- 防止相机运动产生不连续跳变或突然加速。
- 处理相机朝向插值，避免镜头反转。
- 避开太阳核心、地形表面和船体的明显穿模。
- 用户拖动/指针操作期间，自动镜头应让出一部分控制权。
- 保留 ORBIT / DRIFT、ENTER、RESET、滚轮进度和移动端输入；如果改造现有控件，确保语义和测试同步更新。
- Escape 应恢复到一致的可交互开场状态，不应只隐藏 UI 而不重置内部状态。

镜头效果应以流畅、可读、令人沉浸为目标，不以移动速度或运动幅度作为质量指标。

## 8. 必须修复的视觉问题

### 问题 A：海面反光出现方块/马赛克感

先检查旧 Shader 是否使用了按网格离散采样、Hash 阈值、阶梯函数或大颗粒的离散高亮。避免只通过模糊或后期遮盖问题。

修复要求：

- 基础海面着色连续、细腻；
- 真实亮点由不规则笔触几何体提供；
- 近景、远景和滚动运镜中均无明显方块图案；
- 动画期间不会周期性出现固定网格或闪烁；
- 反光具备方向、断续、空间尺度和色彩层次。

### 问题 B：标题与太阳/水平线重叠

- 桌面版让标题、太阳和水平线形成清楚的层级。
- 不要简单把标题缩得很小。
- 移动版单独验收，不能假设桌面布局自动适配。
- 确保 ENTER、相机按钮与底部控制不被遮挡。

### 问题 C：过度依赖后期特效

先校正构图、几何体、色彩与空间层次，再加 Bloom、辉光和雾。不要通过增加 Bloom 来掩盖没有体积的笔触或错误的海面颜色。

## 9. 性能策略

桌面和手机浏览器都要考虑，但对没有实测的设备不可承诺性能指标。

建议按以下顺序优化：

1. 控制笔触数和每条笔触的采样点数。
2. 合并 BufferGeometry / 减少 draw calls。
3. 将连续动画放到 GPU，避免每帧遍历所有笔触。
4. 减少昂贵的 Shader 分支和重复计算。
5. 根据距离或设备能力做细节等级、笔触密度或后期质量调整。
6. 限制 renderer pixel ratio，考虑低性能设备策略。
7. 检查重复创建 Vector、临时对象、RenderTarget 和材质所带来的开销。
8. 正确释放不用的 Geometry、Material、纹理和 RenderTarget。

至少观察开场、沉浸式、海面近景三个状态。浏览器自动化中的 SwiftShader 结果只能证明功能能运行，不代表真实 GPU 性能。若没有真实手机测试，必须如实标注。

## 12. Git、Actions 与部署

### Git 安全

- 每次编辑前先检查远程 HEAD。
- 避免覆盖最新提交或其他人尚未纳入的修改。
- 优先在独立分支提交并打开 Pull Request。
- 如果环境限制只能写默认分支，必须确认分支当前 HEAD，并避免强推。
- 不提交凭证、API Key、\`node_modules\` 或无关的本地缓存。
- 提交前查看 diff 与改动文件清单。

### CI / Pages

检查 \`.github/workflows/monet-sunrise-3d.yml\`，保证工作流先执行构建和 QA，再尝试发布。

当前仓库此前出现过 GitHub Pages 创建失败（权限/API 返回资源不可访问一类错误）。这只是待重新验证的历史线索，并不代表当前状态仍然相同。

- 重新检查当前工作流运行结果和日志。
- 不要把测试失败后的构建物部署出去。
- 如果 Pages 未启用或 GitHub App 权限不足，明确给出实际错误和需修改的设置。
- 只有在真实访问线上 URL 并确认内容与新版本匹配后，才可以报告“已部署/已上线”。
